## 1. 合并结论摘要

- **接口面**：三方共 **119** 条命令 → 去重后 **116** 个统一命令（含 12 条新移植）。
- **命名冲突极小**：仅 `open_recycle_bin` 一处同名；另有 3 处语义重复可合并。
- **版本线高度一致**：两个 Tauri 项目同为 React 19 / TS 5.8.3 / Vite 7 / Tailwind 4，前端收敛成本低。
- **最大工程量在 light-c**（后端 32,851 行 / 前端 23,448 行），占合并总量的 ~76%。
- **最危险的交互点**：M4 空间腾挪（迁移+Junction）与 M3 孤儿目录清理**会互相破坏**，必须做双向保护（见 C1）。
- **许可证风险集中在 light-c**，其余两个为 MIT，可自由分发。

## 5. 关键冲突与消解方案

### C1 ⚠️ 高危：AppData 迁移（M4）与孤儿目录清理（M3）互斥

**机制**：M4 把 `%LOCALAPPDATA%\Foo` 移到 `G:\Yugongyipan\Local\Foo` 并在原位留下 **Junction**。
M3 的 `scan_orphan_dirs` 会枚举 AppData 顶层目录并按知识库判定"无主 → 可清理"。

**后果**：若 M3 未识别 Junction，会把已迁移目录看成"残留空壳"→ 清理掉 Junction →
**应用数据仍在 G 盘，但 C 盘入口消失，软件直接失效**。这是本次合并中唯一可能造成用户数据不可用的问题。

**现状差异**：
- WindowsClear 已有 `scanner.rs::is_symlink_or_junction` 保护（源码中 3 处引用）；
- disk-butler 的孤儿扫描**没有**任何 junction/reparse point 检测（其二进制字符串中无相关 API）。

**消解（必须实现）**：
1. M3 的 `scan_orphan_dirs` 前置过滤：对每个候选目录读属性，命中 `FILE_ATTRIBUTE_REPARSE_POINT` 一律跳过；
2. 建立**双向共享**的 `protected_paths` 集合：M4 迁移历史中所有 `source_path` + 所有 Junction 路径写入；
   M3 清理前二次校验该集合，命中即拒绝并提示"该目录已迁移至 G:\…"；
3. M4 的 `restore_migration` 与 M3 的孤儿清理**不可并发**：加全局互斥锁（同一时刻只允许一个写操作）；
4. 清理结果 UI 中把"已迁移目录"单独成组显示为只读。

### C2 窗体与 CSP 取舍

| 项 | disk-butler | light-c | 合并决策 |
| --- | --- | --- | --- |
| 窗体装饰 | 原生边框 | `decorations: false` 自绘标题栏 | **保留原生边框**（减少自绘标题栏的实现与适配面） |
| CSP | 严格（`script-src 'self'` 等） | `null`（无 CSP） | **保留 disk-butler 的严格 CSP**；light-c 的前端为内联样式，`style-src 'unsafe-inline'` 已覆盖，脚本侧不得放开 |
| devUrl 端口 | 1420 | 1666 | **1420** |
| 窗口尺寸 | 1200×800（min 980×660） | 820×690 | **1200×800**（模块更多，需要更大画布） |

### C3 安装模式与提权模型统一

- disk-butler：`nsis.installMode = perMachine`（因需安装 LocalSystem 扫描服务 `DiskButlerScanSvc`）
- light-c：`currentUser`
- **决策**：取 `perMachine`。同时 M4（建 Junction、结束进程）与 M5（DISM/注册表/驱动）都需管理员 →
  统一提权入口：**以 light-c 的 `runtime.rs`（31KB 提权封装）为主**，并合并 disk-butler 0.8.0 的修复
  ——提权取消必须用专用退出码 `1223 (ERROR_CANCELLED)` 判定，不能用 `exit code == 1`（1 会被 inner 脚本的正常返回误判）。
- `installerHooks`：合并 disk-butler 的 `hooks.nsi` 与 light-c 的 `nsis/installer-hooks.nsh`。

### C4 自动更新会指向错误仓库（需决策）

light-c 的 updater 端点硬编码 `github.com/Chunyu33/light-c/releases/latest/download/latest.json` 并内置其 minisign 公钥。
合并产物若不改，会提示"升级到 LightC"。且引入 `reqwest` 会**打破 disk-butler 的"零网络"设计原则**（其 README 明确承诺零网络请求）。

**选项**：
- **(a) 关闭自动更新**（`createUpdaterArtifacts: false`，移除 updater/reqwest）→ 保住零网络，体积最小。**推荐**。
- (b) 保留但改为自有仓库端点 + 自签 minisign 密钥 → 需自建 Releases 仓库与密钥管理。

### C5 前端 API 层与调用点改写

两边各有独立 `invoke` 封装（disk-butler 直接 `invoke("cmd")`；light-c 集中在 `src/api/commands.ts`）。
合并后建立单一 `src/api/` 分层，需改写的调用点：

| 旧调用 | 新调用 |
| --- | --- |
| `get_local_drives` | `get_drives` |
| `get_cleanup_history` | `get_cleanup_stats` |
| `open_in_folder` | `reveal_in_folder`（走 opener 插件） |
| disk-butler 内联 `invoke("scan_drive")` 等 | 统一收敛到 `src/api/` |

### C6 两套 MFT 引擎并存

| 引擎 | 归属 | 用途 |
| --- | --- | --- |
| `ntfs-reader 0.4` crate + 特权服务 | disk-butler | TreeMap 全盘扫描、`DiskButlerScanSvc` 命名管道 |
| 自研 `mft_core.rs` / `mft_scan.rs` / `mft_discovery.rs` | light-c | 大文件、热点目录、磁盘增长、AI 模型发现 |

**短期**：并存，互不干扰（不同入口、不同用途）。
**代价**：体积与维护成本翻倍，两套解析器对损坏 MFT 的容错行为可能不一致。
**中期建议**：以 light-c 自研引擎为唯一实现（它覆盖 4 个业务场景，且不依赖外部 crate 版本），
disk-butler 的 TreeMap 与特权服务改为调用它 —— 但这会牵动 `DiskButlerScanSvc` 的协议，属较大重构，建议放到 P8 之后。

### C7 图标库与状态层对齐

- `lucide-react`：disk-butler `^1.27.0` vs light-c `^0.563.0`，**两版图标命名集合不同**。
  取 1.27 后需批量替换 light-c 中已改名/移除的图标名（届时以 `tsc` 报错为准逐个修）。
- 状态层：disk-butler 用 React 内置 state（单包 425KB，无 store）；light-c 用 `zustand` + `react-query`。
  **以 light-c 的状态层为准**（模块数量决定需要集中状态），disk-butler 的页面改写为读写同一 store。

### C8 ⚠️ 必须兼容用户现有的 WindowsClear 配置（硬约束）

用户机器上已有真实数据：

```json
// E:\C盘清理3种\config.json  （WindowsClear 生成）
{ "version": 1,
  "target_root": "G:\\Yugongyipan",
  "scan_sources": [ LocalAppData, RoamingAppData, Program Files,
                    Program Files (x86), ProgramData ] }   // 5 项，全部 enabled
```

这意味着 **G 盘上极可能已存在真实迁移数据与 Junction**。因此：

1. M4 的 `get_relocate_config` / `save_relocate_config` 必须**原样读写该文件的格式与位置**，不得改用 Tauri appDataDir；
2. 迁移历史（`history.rs` 落盘的 `MigrationRecord`）同样必须原路径读取，否则 C1 的保护名单会失去历史数据，
   导致**已迁移目录被 M3 判定为孤儿**；
3. `target_root = G:\Yugongyipan` 属用户既有选择，合并后默认值不得覆盖。

## 6. 交互风险矩阵

|  | M3 清理 | M4 迁移 | M5 瘦身 | M7 DISM |
| --- | --- | --- | --- | --- |
| **M3 清理** | — | ⛔ **C1 互斥（致命）** | ⚠️ 两者都可能动 AppData 缓存，需去重 | ⚠️ DISM 后 WinSxS 缩小，M3 的规则需重算 |

| **M5 瘦身** | ⚠️ 图标缓存/注册表项可能被 M3 重复计入 | ⚠️ 同上 | — | ⚠️ WinSxS 双方都有入口，需合并为一个 |
| **M7 DISM** | ⚠️ 需串行 | — | ⚠️ 需串行 | — |

**统一规则**：所有**写操作**（删除/迁移/注册表/服务）共用一把全局互斥锁，串行执行；扫描类只读操作可并行。
