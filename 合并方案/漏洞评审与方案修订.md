## 一、先纠正我自己的错误：一个被实测证伪的假设

### H1 ❌ 原假设：`fs::remove_dir_all` 会穿透 Junction 删除目标盘数据

v1.0 我推断 disk-butler 的孤儿目录清理若命中 WindowsClear 留下的 Junction，会**穿透删除 G 盘上的真实数据**。**实测证伪。**

**实测方法**（`rev/junction_test.py`、`rev/junction_test2.py`）：在工作区 `.tmp` 下建 junction → 指向含标识文件的"真实数据"目录，分别用 8 种删除原语删除链接，观察目标数据是否幸存。

**实测结果矩阵**：

| # | 删除原语 | 链接被删 | **目标数据** | 判定 |
| --- | --- | --- | --- | --- |
| ① | Python `shutil.rmtree(junction)` | ✅ | ✔ 完好 | 安全 |
| ② | `cmd rmdir /s /q` | ✅ | ✔ 完好 | 安全 |
| ③ | 模拟 `remove_dir_all`（lstat 判链接） | ✅ | ✔ 完好 | 安全 |
| ④ | `RemoveDirectoryW`（Win32 正确原语） | ✅ | ✔ 完好 | 安全 |
| ⑤ | **`cmd del /s /q`** | ❌ 残留 | ✘ **被删** | ⛔ **穿透** |
| ⑥ | shell 的 `Remove-Item -Recurse -Force` | ✅ | ✔ 完好 | 安全 |
| ⑦ | **`robocopy <空> <junction> /MIR`** | ❌ 残留 | ✘ **被删** | ⛔ **穿透** |
| ⑧ | `RemoveDirectoryW`（复测） | ✅ | ✔ 完好 | 安全 |

**关键实测数据**：
```
os.path.islink(junction)      → False     # Python 不把 junction 当符号链接
os.path.isjunction(junction)  → True      # Python 3.12+ 有专门的 junction 判定
reparse point 属性            → True
```

**由此得到两条硬结论**：

1. **`std::fs::remove_dir_all` / `rmdir /s` / `Remove-Item -Recurse` 对 junction 是安全的** —— Windows 不会递归跨越 junction 边界。v1.0 的"穿透删除"推断**不成立**。
2. **但 `del /s` 与 `robocopy /MIR`（镜像同步类）确实会穿透** —— 它们按"路径内容"语义工作，会走进 junction 删掉目标盘数据，**且链接本身还残留**（用户完全不会察觉数据已毁）。

**已核查：三方源码均未使用 `del /s` / `robocopy` / `xcopy /E`。**（全仓库检索无命中）
→ 因此**这不是现存漏洞，而是必须写入规范的禁用清单**。见修订项 R1。

## 二、确认的缺陷清单

### 🔴 P0 —— 公开发版前必须修

#### V1 迁移备份落在 `%TEMP%`：失败即数据滞留，且会被本工具自己的清理功能删掉

**位置**：`src_wclear/src/core/mover.rs:562`（备份根目录）、`:735`、`:745-746`

```rust
// :562  备份根 = %TEMP%\WindowsClear\backups
let backup_root = std::env::temp_dir().join("WindowsClear").join("backups");
// :731-749  建 junction 失败时
Err(e) => {
    let _ = fs::remove_dir_all(source);                  // 吞错
    fs::rename(&backup, source).context("恢复源目录失败")?;  // ← 若这步失败…
    Err(e)
}
```

**缺陷链条**：
1. `place_junction_with_backup` 先把 `source` **rename 到 `%TEMP%\WindowsClear\backups\`**（`source` 位置此刻为空）
2. 建 junction；失败则尝试 `rename(backup → source)` 恢复
3. 若恢复也失败（源位置被半成品目录占用 / 权限 / **backup 在另一卷导致跨卷 rename 失败**），函数返回 Err，**而用户的源数据仍滞留在 `%TEMP%\WindowsClear\backups\Foo.windowsclear_bak_<ts>`**
4. **触发前提**：junction 创建失败 **且** 恢复 rename 失败
5. **后果**：`%TEMP%` 是**所有清理工具的标准清理目标**。合并后本应用的 **M3 一键清理**（含"系统临时文件"分类）与 **M5 系统瘦身**（`SystemRoot\Temp` 清理）都会把 `%TEMP%` 当垃圾清掉 → **永久数据丢失**

> **这是本次评审发现的最高危缺陷**，且是**合并行为本身放大的**：单独用 WindowsClear 时，它的清理能力有限；合并后清理能力变强，反而把这个隐患激活成真实的数据丢失路径。

**修复（R2）**：
- 备份目录**必须落在与源同卷的持久位置**（`source.parent()/.db-migrate-backup/<name>.<ts>`），禁止使用 `%TEMP%`
- 恢复失败时**不得静默返回**，必须在 UI 显示"源数据暂存于 `<具体路径>`，请勿删除"并提供一键还原入口
- 迁移启动时把"暂存区路径"写入**独立的持久登记表**（不能只写日志），供下次启动自动检测残留

#### V2 孤儿目录清理会删掉已迁移目录的 Junction（入口丢失）

**位置**：disk-butler `scan_orphan_dirs` / `clean_orphan_dirs`（`src078/src-tauri/src/lib.rs:317`、`knowledge.rs`）

**已核验事实**：
- 全仓库检索 `reparse|junction|symlink_metadata|FILE_ATTRIBUTE` → **孤儿扫描路径上零检测**
  （唯一命中 `cleanup.rs:1508` 的注释是**它自己写临时文件时的防御**："避免固定 %TEMP% 路径被同账户进程预置 junction"，说明作者意识到该攻击面但未覆盖孤儿扫描）
- 判定条件 = 目录名命中 `data/orphan-dirs.txt`（**16 条**）**且**无在装软件别名匹配

**触发前提**（精确化，比 v1.0 更收敛）：
1. 用户用 M4 迁移了某个命中知识库的目录（如 `Discord`、`obsidian`、`CloudMusic`、`pcsuite`…），C 盘留下 junction
2. 该软件**之后被卸载**（否则别名匹配 → 判定"有主"，安全）
3. 用户运行 M3 的孤儿目录扫描并清理

**后果**（按实测修正）：**不会**穿透删除 G 盘数据（实测安全），但会：
- 删掉 C 盘的 junction → **应用的入口路径消失**（若软件被重装/残留服务仍在引用，直接报错）
- G:\ 上的数据成为**无人回收的孤儿**（数 GB 白占空间，用户不知道它的存在）
- WindowsClear 的迁移历史留下**失效记录**（下次 restore 必然失败）

**修复（R3）**：见第四节 R3。

#### V3 迁移历史与配置在 legacy 路径，合并后读不到 → 保护名单为空

**已核验的具体路径**（v1.0 只写了"必须兼容"，未给出路径）：

| 文件 | 实现 | 实际位置 |
| --- | --- | --- |
| 配置 | `config.rs:26-30` `current_exe().parent().join("config.json")` | **exe 同目录**（用户现为 `E:\C盘清理3种\config.json`） |
| 迁移历史 | `history.rs:22` `ProjectDirs::from("com","tanaer","WindowsClear").data_local_dir()/history.json` | `%LOCALAPPDATA%\tanaer\WindowsClear\data\history.json` |

**缺陷**：合并后 exe 位置必然变化（装入 `C:\Program Files\...`），**两处都会读不到**。
**后果**：`protected_paths` 保护名单为空 → **V2 必然触发**，且所有既有迁移记录丢失（用户无法回滚已迁移目录）。
**修复（R3）**：启动时按优先级探测 + 一次性导入，见 R3。

#### V4 light-c 删除护栏硬编码 `c:\` 盘符

**位置**：`src_lightc/src-tauri/src/cleaner/safety_constants.rs:8-33`

```rust
pub const PROTECTED_PATH_PREFIXES: &[&str] = &[
    "c:\\windows\\system32",
    "c:\\windows\\syswow64",
    ...
    "c:\\program files",
    "c:\\$recycle.bin",
    ...
];
```

**缺陷**：前缀匹配全部写死 `c:\`。系统盘不是 C: 时（或对非系统盘操作时）**整套护栏完全失效**。
对照：disk-butler 用 `is_c_drive_root(mount)` 做卷判断，不硬编码（`cleanup.rs:1151`）。

**附带缺陷**：前缀匹配存在边界误判 —— `c:\program files` 会匹配 `c:\program files backup`（方向安全，但语义不严谨）。同文件的 `is_rebuildable_system_cache_path` 做了正确的边界校验（且带反伪造单测：`Support2`、`ServiceEvil`、嵌套伪造路径），**应把同一套边界方法推广到 `PROTECTED_PATH_PREFIXES`**。

**修复（R1）**：护栏改为运行时由 `%SystemDrive%` / `%SystemRoot%` / `%ProgramFiles%` 环境变量展开生成，并统一采用 `is_rebuildable_system_cache_path` 的"盘符根边界 + 目录名完整边界"判定法。

### 🟠 P1

#### V5 `kill_process` 无任何安全校验

**位置**：`src_wclear/src/core/proc_mgr.rs:126-145`

```rust
pub fn kill_process(pid: u32) -> Result<()> {
    let handle = OpenProcess(PROCESS_TERMINATE | PROCESS_QUERY_LIMITED_INFORMATION, false, pid)?;
    let res = TerminateProcess(handle, 1);   // ← 直接终止，无任何校验
```

**缺陷**：PID 来自 `RmGetList`（Restart Manager），**可能包含系统关键进程**（RM 会返回任何持有文件句柄的进程，包括 `explorer.exe`、`svchost.exe`、安全软件、甚至会话关键进程）。无进程名获取 → 无法展示给用户确认；无黑名单 → 可能终止关键进程导致系统不稳定或用户未保存数据丢失。
另：`PROCESS_QUERY_LIMITED_INFORMATION` 已请求，但**没有调用 `QueryFullProcessImageNameW` 取进程名**，等于放弃了最关键的判据。

**修复**：终止前必须 ① 取进程名+路径 ② 排除系统关键进程/自身/父进程/会话 0 进程 ③ 在 UI 中逐个列出（名称+路径+发布者）由用户勾选确认 ④ 默认只"提示"不"自动杀"。

#### V6 静默跳过 symlink + junction 被当普通目录递归复制

**位置**：`mover.rs:309-312`、`mover.rs:527-530`

```rust
if file_type.is_symlink() {
    logger::log(&format!("skip symlink entry={:?}", src_path));
    continue;                              // ← ① 静默跳过，目标缺内容但迁移仍判成功
}
```

**实测依据**：`os.path.islink(junction) == False` → **junction 不会命中 `is_symlink()`**，会被当作**普通目录递归复制**，复制的是**链接指向的真实内容** → ② 体积膨胀 / 重复数据。

**后果**：① → **静默数据不完整**（最难排查的一类缺陷）；② → 迁移耗时与目标盘占用远超预期（AppData 中 junction 常见：浏览器、VS Code、Electron 应用）。

**修复**：用 `FILE_ATTRIBUTE_REPARSE_POINT`（而非 `is_symlink`）统一识别 reparse point，按策略处理：
- 目录 junction/symlink：**不复制内容**，在目标侧**重建等价链接**（或标记为"跳过并告警"）
- 文件 symlink：重建链接或记录到"未迁移清单"
- 任何跳过都必须**计入报告的"跳过项"并在 UI 明示**，不允许静默

#### V7 迁移只保留 mtime，丢失 ACL / ADS / 硬链接 / 稀疏属性

**位置**：`mover.rs:752-786`（自实现 `BufReader`→`BufWriter` 逐块复制，仅 `set_file_mtime`）

**缺陷**：丢失 NTFS ACL（权限）、备用数据流（ADS）、硬链接关系、稀疏/压缩属性。
**触发前提**：迁移源包含需要 ACL 的目录 —— **用户的 config.json 里 `Program Files`、`Program Files (x86)`、`ProgramData` 全部 enabled** → 这类目录 ACL 承载功能语义，丢失后程序可能启动失败或行为异常。
**另外**：AppData 中大量文件是硬链接（Electron/Chromium 系），逐块复制会**实体化为独立副本**，体积暴涨。

**修复**：改用 `SHFileOperationW(FO_COPY)` 或 `CopyFile2`（保留 ACL/ADS/属性），或 `CopyFileEx` + 显式 `SetNamedSecurityInfo` 回写 ACL；对硬链接用 `FindFirstFileNameW` 检测并重建（或至少计入"未保留属性"报告）。

#### V8 跨盘迁移依赖 `cmd /C mklink /J`，参数转义不可靠

**位置**：`mover.rs:800-812`

```rust
let output = Command::new("cmd").args(["/C", "mklink", "/J"]).arg(link).arg(target).output()?;
```

**缺陷**：`cmd.exe` 的参数解析规则与标准 Windows 进程不同，路径含 `&`、`^`、`(`、`)`、空格 时可能**失败或被注入额外命令**（如 `C:\A & B\Foo`）。AppData 下含空格与 `&` 的目录名真实存在。
**同时修正一处事实错误**：`mklink /J`（目录联接）**不需要管理员权限**（任何用户可建本地路径链接）。真正需要管理员的是"结束其他用户的进程"。v1.0 设计文档与 WindowsClear README 在此处表述有误。

**修复**：改用 `DeviceIoControl(FSCTL_SET_REPARSE_POINT)` + `REPARSE_DATA_BUFFER` 直接创建 junction，彻底摆脱 `cmd.exe`；或以 `CreateProcessW` 传 `lpApplicationName="cmd.exe"` 并用 `--%`/双引号严格转义。

#### V9 前端可传任意路径给删除接口，违反 disk-butler 红线 1

**位置**：light-c `delete_files` / `enhanced_delete_files` / `delete_deep_junk_files` / `delete_leftovers_permanent`（接受 `paths: Vec<String>`）

**缺陷**：前端直接传路径 → 校验只能靠后端的 `safety_constants` 兜底（**最后防线而非结构防线**）。
对照 disk-butler 自己的红线（`docs/RULES-SECURITY.md` §3.1）：
> **不信任前端直传路径**：涉及提权/删除/停进程的入口，一律后端按 `id` 重读目标，前端只传 `id`。

**修复（R1）**：合并后统一为 **id 模型** —— 前端只传清理项 id + 勾选集合，后端**当场重扫**得到允许集合，再对每个待删路径做 `canonicalize` 校验：
- `canonicalize` 会**解析 junction 到真实目标** → junction 指向 G 盘的路径将不在 AppData 允许根下 → **自动拒绝**（这正好是 V2 的第二道结构性防线）
- 校验"非安全根本身"、"starts_with 允许根"

## 三、经核验排除的风险（诚实记录，避免后续重复排查）

| 原疑点 | 核验结果 | 证据 |
| --- | --- | --- |
| 管道 DACL 若为默认，本机任意用户可投递 scan 请求 | **已排除（实现优于假设）** | `svc.rs:40` 显式 SDDL `D:(A;;GA;;;SY)(A;;GA;;;BA)(A;;GRGW;;;AU)`；`:68` 带 `PIPE_REJECT_REMOTE_CLIENTS`（拒远程）；`:69` 单实例；`:95` `MAX_REQUEST_BYTES=4096`（限长度）；`:118` 指令白名单仅接受 `"scan"`；文件头注释声明"不接受任何写操作指令" |
| 服务 DACL 过宽 | **已排除** | `disk-butler-svc.rs:129` 与逆向提取的 SDDL **逐字一致**；AU 仅得 `RP`(启动)+查询，无 `WP`(停止)/`DC`(改配置)。注释明确"最小授权" |
| 服务长期驻留 | **已排除** | `start_type: OnDemand` + `run_server_once`（用完即停），无常驻进程 |
| 三方使用会穿透 junction 的危险原语 | **已排除（当前无）** | 全仓库检索 `robocopy`/`xcopy`/`del /s` **零命中**；删除统一走 `std::fs::remove*` 与 shell 的 `Remove-Item -Recurse`（实测均安全） |
| 进度推送淹没 IPC | **已排除** | `svc.rs:26` 已有 200ms 节流 + 阶段变化立即推 |

**唯一保留的低危项（按 SOP 诚实登记）**：管道对 `AU` 授予 `GRGW`，**本机任意已认证用户可请求一次全盘 MFT 扫描并取得完整文件树（含全盘文件名）**。单用户家用机可忽略；多用户/共享机器属低危信息泄露。触发前提：本机存在其他非特权用户。目标磁盘加密/多用户场景建议在 UI 中提示。

另：单实例管道 + "用完即停"意味着本地用户可**抢先连接造成合法客户端 DoS**（低危，单用户机可忽略）。

## 四、方案修订项（并入 `合并设计.md`）

### R1 统一删除引擎（唯一原语 + 禁用清单 + 双层护栏）

```
所有删除必须经 delete_engine::remove(path, mode)
├─ 第 0 层｜结构性：id 模型（前端只传 id，后端当场重扫允许集合）      ← 采纳 RULES-SECURITY 红线 1
├─ 第 1 层｜路径校验：canonicalize 解析 junction → 校验在允许根下 + 非根本身
│                     + 运行时展开的 PROTECTED_PATH_PREFIXES 边界校验   ← 修 V4
├─ 第 2 层｜属性校验：FILE_ATTRIBUTE_REPARSE_POINT → 拒绝删除（或走"解链"专用通道）
├─ 第 3 层｜原语：RemoveDirectoryW / remove_dir / remove_dir_all / trash   ← 唯一允许集合
└─ 审计：每次删除写操作台账（路径、大小、时间、结果、模式）
```

**⛔ 全局禁用原语清单（写入代码规范 + CI 检查）**：

| 禁用 | 原因 | 实测证据 |
| --- | --- | --- |
| `del /s` | **穿透 junction 删除目标盘数据，且链接残留** | 实测 ⑤ ✘ 数据被删 |
| `robocopy /MIR`、`xcopy /E` 等镜像同步式删除 | 同上 | 实测 ⑦ ✘ 数据被删 |
| 前端可传任意路径的删除接口 | 违反信任边界红线 1 | RULES-SECURITY §3.1 |

### R2 迁移安全网（对应 V1 / V6 / V7 / V10 / V11 / V12 / V13）

| 项 | 要求 |
| --- | --- |
| 备份位置 | **必须与源同卷且持久**（`<source.parent>/.db-migrate-backup/`），**禁止 `%TEMP%`** |
| 残留登记 | 暂存区路径写入独立持久登记表；启动时自动检测并提示还原 |
| 空间预检 | 迁移前校验目标盘 `剩余 ≥ 源 × 1.1` |
| reparse 处理 | 按 `FILE_ATTRIBUTE_REPARSE_POINT` 识别（**不用 `is_symlink`**）；目录链接重建链接、文件链接重建链接，跳过项**必须明示不可静默** |
| 属性保留 | 改用保留 ACL/ADS/属性的复制原语；硬链接检测并重建或计入报告 |
| 取消语义 | 增加 Cancel；清理 `.partial`；写登记表 |
| 命名 | 修 `with_extension` 误用 |
| **实证验收** | 用例必须覆盖：含 junction 的目录、含空格与 `&` 的路径、目标盘空间不足、迁移中断后残留检测、回滚——**这 5 个场景是 P2 的出口标准** |

### R3 迁移-清理互斥与 legacy 导入（对应 V2 / V3）

**legacy 导入（一次性，必须在首次启动时完成）**：

| 探测源 | 路径 | 用途 |
| --- | --- | --- |
| ① 新位置 | `<appDataDir>/relocate/config.json` | 合并后主位置 |
| ② legacy 配置 | **原 WindowsClear exe 同级目录** `config.json`（含 `target_root`） | 恢复用户既有 `G:\Yugongyipan` 选择 |
| ③ legacy 历史 | `%LOCALAPPDATA%\tanaer\WindowsClear\data\history.json` | **重建 `protected_paths` 保护名单**（V2 的关键） |
| ④ 兜底 | 提示用户手动指定旧安装目录 | 覆盖便携版/换机场景 |

**双向保护集合 `protected_paths`**：
- 来源：③ 的迁移记录的 `source_path` ∪ 当前磁盘上所有 reparse point 目录
- 消费：M3 `scan_orphan_dirs` 前置过滤（跳过并标记 `migrated`）+ `clean_orphan_dirs` 清理前二次校验
- 交互：M3 结果页把"已迁移目录"**单独成组、只读展示**，并给出"该目录已迁移至 `G:\...`"的说明与"打开目标位置"按钮

**互斥**：M4 迁移/回滚 与 M3 清理 共用一把全局写锁，串行执行。

### R4 统一提权架构

| 项 | 结论 |
| --- | --- |
| 保留 `DiskButlerScanSvc` | **保留**。已核验其安全实现优于假设（拒远程 + 最小授权 + 限长 + 指令白名单 + 用完即停），是"免管理员秒级扫描"的关键，且是 disk-butler 底座的核心资产 |
| 提权入口收敛 | 统一走**不落地脚本**方案（`-EncodedCommand` UTF-16LE+Base64 内联，经环境变量传参），采纳 `RULES-SECURITY` 红线 2；light-c 的 `runtime.rs` 按此改造 |
| UAC 取消判定 | 必须用专用退出码 **1223 (ERROR_CANCELLED)**，禁止用 `exit code == 1` 判定（1 会被 inner 脚本正常返回误判）—— 采纳 disk-butler 0.8.0 的既有修复 |
| 权限时机 | 启动时检测并提示，**按需提权**而非全程管理员 |
